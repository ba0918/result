# collect()メソッド実装必要性調査報告書

**調査日時**: 2025-07-14 17:36:34  
**調査者**: Claude Code  
**調査目的**: PHP Result/Option型ライブラリにおけるcollect()メソッドの実装必要性を評価する

## エグゼクティブサマリー

本調査の結果、**現時点でcollect()メソッドの実装は推奨しない**という結論に至りました。

主な理由：
1. **PHPの型システムの制約**: Rustのようなジェネリクスと型推論の不在
2. **イテレータエコシステムの未成熟**: PHPにはRustのような統一的なIteratorトレイトがない
3. **限定的な実用性**: PHPの既存のarray関数群で多くのユースケースがカバー可能
4. **設計複雑性**: 型安全性を保ちながらの実装が困難

代替として、**より実用的なユーティリティメソッド**の実装を推奨します。

## 1. 調査背景

### 1.1 Rustのcollect()メソッドとは

Rustにおけるcollect()は、イテレータから値を収集して別のコレクション型に変換する強力なメソッドです。

```rust
// Rustでの基本的な使用例
let numbers: Vec<i32> = vec![1, 2, 3];
let doubled: Vec<i32> = numbers.iter().map(|x| x * 2).collect();

// Result型での特殊な振る舞い
let strings = vec!["1", "2", "3"];
let numbers: Result<Vec<i32>, _> = strings
    .iter()
    .map(|s| s.parse::<i32>())
    .collect(); // 全て成功すればOk(Vec)、一つでも失敗すればErr
```

### 1.2 特徴的な振る舞い

**Result<T, E>のコレクション**:
- `Iterator<Item = Result<T, E>>` → `Result<Collection<T>, E>`
- 全要素が`Ok`なら`Ok(Collection)`を返す
- 一つでも`Err`があれば最初の`Err`を返す（短絡評価）

**Option<T>のコレクション**:
- `Iterator<Item = Option<T>>` → `Option<Collection<T>>`
- 全要素が`Some`なら`Some(Collection)`を返す
- 一つでも`None`があれば`None`を返す

## 3. PHPでのcollect()実装における技術的制約

### 3.1 型システムの制約

**問題点1: 真のジェネリクスの不在**
```php
// PHPではこのような型定義ができない
interface Collectable<T, C extends Collection<T>> {
    public function collect(): C;
}
```

**問題点2: 型推論の不在**
```php
// Rustではコレクション型を推論できるが...
let v: Vec<_> = iter.collect(); // 型が推論される

// PHPでは明示的な型指定が必要
$result = $iterator->collect(); // 戻り値の型が不明確
```

### 3.2 イテレータの非統一性

PHPには統一的なIteratorトレイトがなく、以下のような複数の形式が混在：
- 配列
- \Iterator インターフェース
- \IteratorAggregate インターフェース
- Generator
- Traversable

### 3.3 パフォーマンスへの影響

```php
// 仮想的なcollect()実装
public function collect(iterable $items): Result {
    $collected = [];
    foreach ($items as $item) {
        if ($item instanceof Err) {
            return $item; // 短絡評価
        }
        $collected[] = $item->unwrap();
    }
    return Ok::of($collected);
}
```

問題：
- 型チェックのオーバーヘッド
- ボックス化/アンボックス化のコスト
- メモリ使用量の増大

## 6. 代替案の検討

### 6.1 より実用的なユーティリティメソッド

```php
// 1. sequence(): 複数のResultをまとめる
class Results {
    /**
     * @param array<Result<T, E>> $results
     * @return Result<array<T>, E>
     */
    public static function sequence(array $results): Result {
        $values = [];
        foreach ($results as $result) {
            if ($result->isErr()) {
                return $result;
            }
            $values[] = $result->unwrap();
        }
        return Ok::of($values);
    }
}

// 2. traverse(): mapとsequenceを組み合わせる
public static function traverse(array $items, callable $fn): Result {
    $results = array_map($fn, $items);
    return self::sequence($results);
}

// 3. partition(): 成功と失敗を分離
public static function partition(array $results): array {
    $oks = [];
    $errs = [];
    foreach ($results as $result) {
        if ($result->isOk()) {
            $oks[] = $result->unwrap();
        } else {
            $errs[] = $result->unwrapErr();
        }
    }
    return [$oks, $errs];
}
```

### 6.2 実用例での比較

```php
// 現在のPHPイディオム
$userIds = [1, 2, 3];
$results = array_map(fn($id) => findUser($id), $userIds);
$users = [];
foreach ($results as $result) {
    if ($result->isErr()) {
        return $result; // エラーを伝播
    }
    $users[] = $result->unwrap();
}

// sequence()を使った場合
$userIds = [1, 2, 3];
$results = array_map(fn($id) => findUser($id), $userIds);
return Results::sequence($results); // より簡潔
```

## 7. 実装方針の決定

### 7.1 推奨事項

**collect()メソッドを実装しない理由**:

1. **技術的制約が大きすぎる**
   - PHPの型システムでは完全な型安全性を実現できない
   - パフォーマンスへの悪影響が懸念される

2. **限定的なROI**
   - 実装コストに対して得られる利益が小さい
   - 既存のPHPイディオムで十分に対応可能

3. **ライブラリの焦点がぼやける**
   - 現在97%+の完成度を持つコア機能に集中すべき
   - 不完全な機能追加は品質低下を招く

## 9. 結論

collect()メソッドの実装は、Rustとの互換性という観点では魅力的ですが、PHPの言語特性と現実的な制約を考慮すると、**実装しないことが最善の選択**です。
